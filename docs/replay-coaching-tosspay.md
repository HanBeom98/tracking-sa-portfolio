# AI 횟수권: 토스페이 공식 API 연결 준비

> 2026-10-28 문서 안내: 공식 API 연결과 TEST 거래의 개발 이력을 보존한 문서다. 현재 구성은 **20회·3,300원·365일**, 비회원 TEST 접근과 공유 한도는 [재심사 체크리스트](tosspay-reapplication-checklist.md#현재-심사-경로), 공개 약속은 [제공·환불 조건](replay-coaching-sales-conditions.md)이 기준이다. 아래 초기 50회 예시와 이전 접근코드·한도는 당시 기록이며 실제 판매·유료 AI 활성화 완료를 뜻하지 않는다.

## 초기 연결과 후속 검증 기록

2026-10-26. 사용자는 토스페이 가맹 신청에서 조건부 환불을 선택해 신청했다고 확인했다. **가맹 승인·계약 조건·운영 키 확인·실제 판매 활성화는 미완료**다. 기본 리플레이 분석은 무료이고 가격/횟수 3,300원/50회는 개발 예시다.

## 공식 자료 활용

외부 SDK나 새 유료 서비스를 추가하지 않고 Node 22의 HTTPS fetch로 공식 JSON API를 사용한다. 토스페이와 토스페이먼츠의 API를 혼용하지 않는다.

| 작업 | 공식 문서 | 현재 구현 |
|---|---|---|
| 결제 생성 | [payments](https://docs-pay.toss.im/reference/normal/create) | 서버 설정 반환 URL, `amountTaxFree:0`, `autoExecute:false`, 발급 토큰과 결제창 URL 검사 |
| 구매자 인증 후 승인 | [execute](https://docs-pay.toss.im/reference/normal/execute) | 상태 조회 → `PAY_APPROVED` 확인 → 승인 → 상태 재조회 |
| 상태·거래 확인 | [status](https://docs-pay.toss.im/reference/common/status) | 모드·주문·토큰·원래 총액·거래번호·환불 잔액 검사 |
| 부분/전액 환불 | [refunds](https://docs-pay.toss.im/reference/common/refunds) | 금액 필수, 고정 환불번호, `idempotent:true`, 결과를 상태 재조회로 대조 |
| 테스트 범위 | [공식 준비](https://docs-pay.toss.im/tutorial/step-1), [테스트](https://docs-pay.toss.im/tutorial/step-6) | 공용 TEST 키로 실제 금전 이동 없이 검증. 현금영수증 발급은 검증 범위 밖 |

## 실제 TEST API에서 확인한 결과

공식 공용 테스트 키로 만든 **동일 테스트 주문 한 건**을 대상으로 사용자가 토스 앱에서 구매자 인증을 마쳤다. 이번 구현의 테스트 클라이언트로 승인·환불·상태 조회를 수행했다. 이전 단계에서 결제 생성과 결제창 URL 발급을 확인했다. 운영 회원/주문/횟수권/DB와 연결하지 않았다.

| 단계 | 실제 확인 결과 |
|---|---|
| 결제 생성·조회 | `TEST`, 개발 예시 3,300원, `PAY_STANDBY`, 결제창 URL 발급 |
| 앱 인증 후 서버 승인 | `PAY_COMPLETE`, 환불 가능 금액 3,300원 |
| 부분환불 | 660원 환불, `REFUND_SUCCESS`, 남은 금액 2,640원 |
| 동일 번호·금액의 멱등 요청 확인 | 추가 환불 없이 2,640원 유지, 환불 거래 1건 유지 |
| 나머지 금액 환불 | 2,640원 환불, 최종 환불 가능 금액 0원, 결제 1건 + 환불 2건 |

실제 API 호출과 로컬 대역 검사는 구분한다. 외부 콜백 수신·사이트 구매 버튼·실거래 키·실제 정산·현금영수증·운영 DB 지급은 시험하지 않았다. 키·결제 토큰·계좌/카드 정보·사용자 인증 정보를 저장소에 남기지 않는다. 외부 시험 실행 기록은 Git 저장소 밖 로컬 작업 기록으로만 보관했다. 반복 실행/부하 테스트/폴링은 하지 않았다.

### 문서와 실제 응답 차이

실제 TEST 환불 응답의 `refundedAmount`는 **-660**이었다. 상태 조회의 `REFUND` 거래에는 문서에 나오는 `refundNo`가 없었고 `transactionId`와 음수 `transactionAmount`가 있었다. 최초 구현은 예상과 달라 환불 완료로 확정하지 않았다. 같은 주문 조회로 성공을 확인하고, 동일 환불번호의 멱등 응답에서 거래번호를 대조했다. 실제 관측을 로컬 회귀 검사에 추가했다.

환불 금액은 정수·정확한 절댓값을 검사하고, 환불 API의 **요청 번호·토큰·거래번호**와 상태 조회의 **동일 거래번호·음수 금액**을 연결한다. 상태에 환불번호가 없다는 이유로 금액만 같은 다른 환불을 승인하지 않는다. 응답의 알려지지 않은 부가 필드는 무시하지만 정합성 필드는 검증한다. 이 TEST 관측이 실거래 모든 결제수단·세금 조합을 검증했다는 뜻은 아니다.

## 서버 코드와 활성화 경계

`cloud-functions/replay-coaching-tosspay.js`의 `createTossPayTestClient`는 기본 비활성, **TEST 키만 허용**한다. 운영 키는 네트워크 요청 전 거절한다. 키는 인자로 주입하며 환경/운영 키를 자동으로 읽지 않는다. 고정 토스 API 주소만 호출하고, 64KB 응답 상한·타임아웃·리다이렉트 금지·오류 메시지 정제를 적용한다. 자동 재시도·폴링·로그/DB/분석 기록을 추가하지 않는다. 콜백 본문·브라우저 복귀 파라미터를 지급 근거로 사용하지 않는다.

`refundPayment`는 테스트용 저수준 API 연결이며 환불 정책 판단이나 DB 잠금을 대신하지 않는다. 현재 단순 과세 구성만 지원하고 복합 과세/봉사료/컵 보증금 등은 거절한다. 정상 응답을 받은 환불은 `refundNo → transactionId`를 서버에 영속 연결해야 한다. 호출 결과가 불명확하면 횟수 예약을 유지하고 같은 거래를 확인한다. 알려진 거래번호로 조회만 할 수 있고, 같은 환불번호의 멱등 재요청은 운영 조정 절차에서 별도로 통제해야 한다. 새 번호로 무작정 재요청하지 않는다. 전액 환불 뒤 응답을 잃고 거래번호도 모르는 경우 등 자동 판별이 어려운 건은 명시적 운영 복구가 필요하다.

`cloud-functions/replay-coaching-tosspay-verifiers.js`는 기존 주문 관리자의 신뢰된 `verifyPayment`/`verifyRefund` 포트 형식으로 변환하는 코드다. 기본 비활성이며, **LIVE 모드의 서버 전용 주문/환불 연결 기록과 신뢰된 상태 조회**를 요구한다. 주문·회원·금액·결제번호 및 원 결제 해시·저장된 환불 요청번호/거래번호가 일치해야 한다. TEST 상태를 지급/환불 증명으로 받아들이지 않는다. 기존 주문 관리자에도 TEST/알 수 없는 모드의 명시적 증명을 거절하는 방어를 추가했다. 모드가 없는 기존 내부 은행 검증 포트 계약은 유지한다.

현재 TEST 클라이언트를 LIVE 증명 검증기에 바로 연결하면 의도대로 거절된다. LIVE 네트워크 클라이언트·배포된 구매/콜백 경로는 미연결이다. 서버 전용 연결 기록·인증 주문 준비・아래 결제 진행 연결 코드는 로컬/Emulator에서 구현·검증했으며 운영 배포하지 않았다. 통합 검사는 합성 LIVE 응답을 사용하며 실제 실거래를 검증한 것이 아니다.

Cloud Functions export·Cloudflare 라우트·브라우저 결제 버튼 활성화·운영 키·운영 DB 쓰기·새 인덱스·의존성은 추가하지 않았다. 아래 저장 경로/필드는 비활성 코드에만 존재한다. 실제 외부 결제 호출은 앞의 공식 TEST 검증에 한정하며, 저장 코드 검사에서 외부 결제 요청을 반복하지 않았다.

## 서버 주문과 결제·환불 연결 기록

`cloud-functions/replay-coaching-tosspay-store.js`는 기본 비활성이고 `TEST` 또는 `LIVE` 모드를 명시해야 한다. 기존 `_replay_coaching_users` 안의 `tosspay_test_v1_<회원해시>` / `tosspay_live_v1_<회원해시>` 아래 `payments/<주문ID>`, `refund_bindings/<환불ID>`를 사용한다. 운영 횟수권 지갑 `credits_v1_<회원해시>`와 TEST 기록이 섞이지 않는다. 기존 재귀 차단 규칙으로 회원·사이트 관리자 클라이언트 모두 접근할 수 없다. 새 규칙/인덱스/실시간 구독/스캔·조회 쿼리/예약 정리 작업은 없다.

- 서버가 만든 주문의 상품·가격·횟수·약관 버전·만료 정책·생성 시각을 고정한다. LIVE 기록은 실제 기존 주문과 대조한다. TEST는 운영 지갑이나 회원 문서를 읽거나 수정하지 않는다. 구매 주문 자체의 생성·회원 인증은 주문 관리자/아래 준비 핸들러의 역할이며, 이 저장소가 임의 가격을 승인하지 않는다.
- 모드·회원·내부 주문ID로 외부 주문번호를 결정한다(50자 이내). 환불도 같은 방식으로 고정 요청번호를 만든다(36자 이내). 프로세스가 재시작돼도 새 번호로 중복 전송하지 않는다.
- 상태는 `prepared → dispatching → ready`다. 외부 요청 전 트랜잭션으로 `dispatching`을 기록하며 동시 요청 중 한 건만 전송권을 받는다. 오류/미확정은 `uncertain`으로 남고 자동으로 전송권을 돌려주지 않는다. 실제 API 호출은 이 저장소 밖에서 수행한다.
- 검증된 결제 응답의 주문번호·금액·모드·토큰·토스 결제창 URL을 대조하고 고정한다. 토큰 해시 표식으로 같은 토큰을 다른 회원/주문에 연결하지 못한다. 준비/미확정 상태의 기록을 결제 완료 증명으로 사용하지 않는다.
- LIVE 환불 기록 생성에는 기존 원장의 미사용 횟수 잠금과 원 결제 해시가 일치해야 한다. 환불 요청번호·금액·수량·원 결제를 고정하고, 완료 거래번호를 별도로 저장한다. 같은 환불 거래번호를 다른 환불에 재사용하지 못한다. 저장소는 돈을 송금하거나 횟수 예약을 풀거나 환불 확정 수량을 변경하지 않는다.
- `loadBinding`/`loadRefundBinding`을 앞의 증명 검증기에 연결할 수 있다. 개인정보 원문·카드번호·계좌번호·API 키·원본 리플레이를 저장하지 않는다. 내부 거래 연결 문서는 서버 전용이다. 브라우저에 원장 문서를 직접 반환하지 않으며, 결제 진행을 명시적으로 연결한 경우에만 소유자에게 토큰이 포함된 검증된 토스 결제창 URL을 전달한다.

### 추가 DB 작업 수

경합 없는 로컬 메모리 계측이며 실제 청구/운영 전체 사용량은 아니다. 트랜잭션 재시도·기존 주문 생성·횟수 지급/환불 원장·인증·용량 예약·다른 사이트 이용은 별도다.

| 저장소 작업 | 읽기 | 쓰기 |
|---|---:|---:|
| LIVE 주문 연결 준비 | 2 | 1 |
| 동일 주문 준비 재확인 | 2 | 0 |
| LIVE 결제 요청 전송권 획득(원 주문 상태 재검사 포함) | 2 | 1 |
| LIVE 결제 토큰·중복 표식 신규 저장(원 주문 재검사 포함) | 3 | 2 |
| 연결 기록 단건 조회 | 1 | 0 |
| LIVE 환불 연결 준비 | 4 | 1 |
| 환불 요청 전송권 획득 | 1 | 1 |
| 환불 거래번호·중복 표식 저장 | 2 | 2 |
| 환불 연결 단건 조회 | 1 | 0 |

운영 사용량은 저장소 밖 로컬 점검 기록으로만 확인했으며 추가 분석 로그나 측정용 DB 쓰기를 만들지 않았다. 저장된 연결 문서 수는 실제 주문·환불 수에 따라 늘어난다. 저장량·보관 정책 확인과 아래 예약 기능의 운영 연결은 여전히 판매 전 필수다.

## 결제 전 지급 공간 예약과 인증된 주문 준비

`cloud-functions/replay-coaching-purchase-capacity.js`와 기존 주문 관리자의 `reserveCapacity: true` 경로는 주문을 만들 때 회원 지갑의 **주문별 잔액 묶음 공간과 수량**을 먼저 확보한다. 기존 지갑 스키마는 유지하고, 서버 전용 `_replay_coaching_users/credit_purchase_capacity_v1_<회원해시>` 한 문서에 제한된 예약 목록과 한국 시간 기준 일별 생성 수를 저장한다. Firestore 전체 저장 용량이나 프로젝트의 무료 할당량을 예약한다는 뜻은 아니다.

- 기본 구현 상한은 회원당 미완료 예약 3개, 신규 주문 10개/일이다. 같은 주문 재요청은 생성 수를 늘리지 않고, 미시작 주문을 취소해도 그날 생성 수는 유지한다. 날짜가 바뀌어도 기존 미확정 예약을 지우지 않는다. 이 수치는 개발용 남용 방지 기준이며 판매 조건 확정과 구분한다.
- 예약·주문 생성은 같은 트랜잭션에서 처리한다. 지급 때도 다른 예약을 포함해 공간을 검사하므로, 기존 내부 지급 경로가 예약 자리를 먼저 차지하지 못한다. 정상 지급은 예약 제거·지갑 추가·주문 완료·결제 중복 표식을 한 번에 확정한다.
- 주문 `checkout.state`는 `reserved → dispatching → funded`이며 불명확한 요청은 `uncertain`으로 유지한다. `reserved`에서만 `closed` 취소와 예약 해제를 허용한다. 결제 시작·취소가 경합하면 한 쪽만 성공한다. 외부 요청 전 `beginCheckout` 다음 LIVE 연결 저장소의 전송권을 확보해야 한다. 결제 토큰 신규 연결도 원 주문 상태를 대조한다.
- 시간이 지났다는 이유로 결제 시작/미확정 예약을 풀지 않는다. 중복 전송으로 복구하지 않으며, 조회·조정·보상 절차는 별도 연결해야 한다. 예약은 계정 삭제/차단·서비스 중단·외부 승인 뒤 DB 장애 등 모든 지급 실패를 해결하지 않는다.

`cloud-functions/replay-coaching-purchase-service.js`의 `createReplayPurchaseHandler`는 **기본 비활성·배포 export 없음**인 주문 준비 HTTP 코드다. 검증된 로그인 토큰의 회원만 자기 주문을 생성·단건 조회·미시작 취소할 수 있다. 요청은 POST JSON 최대 2KB이며, 클라이언트 가격·수량·회원ID·결제 토큰·완료 증명 필드는 거절한다. 가격/수량/유효기간은 주입된 서버 상품 정책에서만 정하고, 생성 요청의 약관 버전이 일치해야 한다. 버전 일치는 실제 구매 동의·미성년자 절차를 수집했다는 뜻이 아니다.

기본 준비 경로 응답은 구매 조건과 주문 상태만 반환하며 `paymentEnabled: false`다. 거래 해시·회원 해시·예약 문서를 반환하지 않는다. 주문 생성 후 연결 기록 준비가 실패하면 같은 주문ID로 복구할 수 있고 새 번호를 만들거나 예약을 자동 해제하지 않는다. 별도 `checkoutEnabled: true`와 신뢰된 LIVE 제공자 코드를 주입한 경우에만 아래 결제 진행 동작을 허용한다. 환불·AI 호출·자동 폴링은 없다. 실제 판매에 연결하려면 인증 구현과 별도로 공개 경로의 요청 빈도 제한도 필요하다. 일별 신규 주문 상한은 반복 조회/재요청에 의한 읽기 비용 상한이 아니다.

### 준비 경로의 로컬 DB 작업 수

경합·재시도 없는 메모리 계측이다. 인증 네트워크·외부 결제·후속 AI 분석·다른 사이트 이용·운영 청구는 포함하지 않는다. 위 저장소 표와 중복되는 단계가 있으므로 전체 거래 비용으로 단순 합산하지 않는다.

| 작업 | 읽기 | 쓰기 |
|---|---:|---:|
| HTTP 신규 주문 + 지급 공간 예약 + 연결 준비 | 8 | 3 |
| HTTP 같은 주문 생성 재요청 | 7 | 0 |
| HTTP 소유 주문 단건 조회 | 1 | 0 |
| HTTP 미시작 주문 취소 | 5 | 2 |
| HTTP 이미 취소한 주문 재취소 | 5 | 0 |
| 내부 `beginCheckout` | 4 | 1 |
| 내부 결제 확인 + 지급(합성 증명, 초기 조회 포함) | 6 | 4 |

검증은 마지막 잔액 묶음 공간의 동시 예약, 기존 지급과의 경쟁, 같은 거래의 중복 지급, 시작/취소 경합, 미확정 예약 유지, 다른 회원 주문 접근 거절, 가격 주입 차단, 비활성 기본값, 저장 실패 후 같은 ID 복구를 포함한다. 실제 Firestore Emulator에서도 트랜잭션 경합과 익명/회원/사이트 관리자 클라이언트 접근 차단을 확인했다. 새 인덱스·의존성·예약 작업·운영 DB 쓰기는 추가하지 않았다.

## 결제 진행과 승인 응답 유실 처리

`cloud-functions/replay-coaching-checkout.js`는 기존 주문 관리자·연결 저장소·증명 검증기를 조합한다. 기본 비활성이고 `mode: LIVE`인 서버 제공자의 `createPayment`/`inspectPayment`/`approvePayment`와 고정 상품 설명을 명시적으로 주입해야 한다. 환경 변수/운영 키를 자동 조회하거나 TEST 클라이언트를 LIVE로 바꾸지 않는다. 제공자는 서버가 관리하는 타임아웃·응답 검증·신뢰된 상태 조회를 구현해야 하며 브라우저/콜백 데이터를 상태 조회로 대신하면 안 된다.

| 단계 | 구현 동작 | 결과 불명확 시 |
|---|---|---|
| 결제창 준비 | 계정·주문·예약 재검사 → 주문 시작 잠금 → 외부 생성 전송권 → 생성 → 모드/주문/금액/토스 URL 대조 후 저장 | 예약과 시작 기록 유지, 새 생성 요청 금지 |
| 같은 결제창 재요청 | 저장된 동일 토스 URL 반환 | 토큰/URL이 저장되지 않았으면 미확정 응답; 추측으로 URL 재구성하지 않음 |
| 구매자 인증 대기/결제 진행 | 신뢰된 상태 조회만 수행, 각각 `awaiting_buyer`/`payment_pending` 반환 | 자동 폴링/승인 없음 |
| 구매자 인증 완료 | `PAY_APPROVED` 및 원 금액 대조, 원 주문에 `checkout.approvalRequestedAt`을 트랜잭션으로 기록한 한 요청만 승인 호출 | 응답 유실 뒤 동일 승인 재전송 금지 |
| 승인 후 확인 | 승인 응답 자체를 믿지 않고 상태 재조회. LIVE 모드·주문·토큰·총액·PAY 거래·환불 이력 대조 후 기존 증명 검증기와 원장으로 지급 | `uncertain`과 횟수 예약 유지 |
| 다음 명시적 완료 확인 | 서버 조회에서 `PAY_COMPLETE`가 확인되면 승인 재호출 없이 미지급 원장 지급 시도 | 계정 차단/만료/DB 장애 등은 조정 대상으로 유지 |
| 이미 원장 지급 완료 | 원장 상태 반환, 결제 조회/승인/추가 지급 생략 | 전액 환불 뒤에도 예전 완료 요청으로 횟수 복원 안 함 |

외부 생성·조회·승인 호출은 모두 Firestore 트랜잭션 밖이다. 트랜잭션 재시도가 외부 호출을 반복하지 않는다. 지급 증명에는 해당 요청에서 갓 조회한 서버 응답의 복사본을 사용하며 전역 캐시나 요청 본문을 사용하지 않는다. 지급 트랜잭션의 완료 응답만 유실된 경우 원장의 `paid` 상태를 통해 중복 지급을 막는다.

공식 [생성 API](https://docs-pay.toss.im/reference/normal/create)는 중복 주문번호의 결제 생성을 거절한다. [승인 API](https://docs-pay.toss.im/reference/normal/execute)는 구매자 인증 후 가맹점 승인을 설명하며, [상태 API](https://docs-pay.toss.im/reference/common/status)는 응답을 받지 못한 거래의 확인에도 사용할 수 있다. 생성 토큰/URL을 저장하지 못한 상태, 정산/외부 환불 상태, 취소 확인 뒤 예약 해제, 승인 전후 계정 삭제/차단·유효기간 경과는 이 코드가 자동 해결하지 않는다. 신뢰된 조정·보상/환불 절차와 콜백 처리가 여전히 필요하다.

인증 HTTP 핸들러에는 `checkout`/`complete` 동작을 추가했다. 두 동작도 검증된 회원과 자기 주문ID만 받으며 가격·토큰·승인 증명 주입을 거절한다. **기본 구매 핸들러 활성화만으로는 결제가 켜지지 않는다.** 별도 결제 옵션과 서버 제공자 구현이 필요하다. 소유자 결제창 URL 응답에는 토큰이 포함되므로 `no-store`로 처리하고 제3자에게 전달하거나 로그/분석에 저장하지 않는다. `get`은 외부 결제를 조회하지 않는 원장 단건 조회다. 아래 구매/복귀 화면은 로컬에서만 연결했으며 배포 라우트·LIVE 네트워크 클라이언트는 미연결이다.

### 결제 진행 경로의 로컬 계측

인증 HTTP부터 원장 응답까지 포함한 로컬 메모리 DB + 합성 제공자 검사다. 트랜잭션 재시도, 인증 네트워크, 제공자 내부의 추가 API 호출, 다른 사이트 기능과 실제 청구는 제외한다. 앞의 단계별 표와 합산하지 않는다. 제공자 호출은 메서드 호출 수이며 실제 외부 요청을 실행한 수치가 아니다.

| HTTP 동작 | DB 읽기 | DB 쓰기 | 합성 제공자 호출 |
|---|---:|---:|---|
| 준비된 주문의 최초 `checkout` | 19 | 4 | 생성 1 |
| 같은 결제창 재요청 | 9 | 0 | 없음 |
| 인증 대기 중 `complete` | 7 | 0 | 조회 1 |
| 인증 후 승인·지급까지 `complete` | 18 | 5 | 조회 2 + 승인 1 |
| 지급된 주문의 `complete` 재요청 | 2 | 0 | 없음 |
| 원장 `get` | 1 | 0 | 없음 |

추가 검사는 동시 생성/승인 1회, 트랜잭션 재시도, 생성/승인 응답 유실, 토큰 저장 실패, 승인 후 DB 지급 실패와 복구, 지급 완료 응답 유실, TEST/금액/거래/URL 불일치, 다른 회원 접근, 전액 환불 후 중복 완료 요청을 포함한다. 실제 Firestore Emulator에서도 동시 처리와 유실 복구를 합성 제공자로 확인했다. 추가 실제 토스/AI 호출·운영 DB 쓰기·새 인덱스·의존성은 없다.

## 로컬 구매·복귀 화면 연결

구매 흐름은 `src/domains/stats/sudden-attack/replay` 안에서 응답 검증(`domain/replay-purchase-response.js`), 상태/계정/주문 관리(`application/replay-purchase-session.js`), 고정 로컬 통신(`infra/replay-purchase-client.js`), 화면(`ui/replay-purchase-flow.js`)으로 나눴다. 일반 무료 페이지는 이 경로를 불러오거나 구매 API를 호출하지 않는다.

개발 진입 조건은 **정확히 `http://127.0.0.1:4173` + `?coaching=review&transport=api&purchase=flow`**다. 배포된 사이트에서 같은 쿼리를 붙여도 실행되지 않는다. 이 플래그는 결제 권한이 아니며, 서버의 구매/결제 활성화·인증·주문 소유권·LIVE 모드 검사를 우회하지 못한다. 현재 정적 로컬 서버에 실제 결제 API를 노출하지 않았다. 브라우저 검사는 요청을 인프로세스의 실제 핸들러와 메모리 DB/합성 결제 제공자로 연결하며, 토스 도메인 이동도 로컬 응답으로 가로채 외부 거래를 만들지 않는다.

| 화면 단계 | 사용자 동작 | 보안·중복 처리 |
|---|---|---|
| 상품 확인 | 로그인 후 서버 가격·횟수·약관 버전·기한 조회 | `product` 동작은 서버 상품 설정만 검증, DB 읽기/쓰기·외부 결제 호출 없음 |
| 주문 준비 | 표시 조건 확인 후 주문 버튼 | 주문번호를 먼저 보관한 뒤 생성 요청. 동시 클릭 방지, 가격/수량/회원ID를 본문에 보내지 않음 |
| 결제창 준비 | 소유 주문의 결제창 요청 후 명시적으로 이동 | 서버가 검증한 토스 URL만 허용. 복수 토큰/다른 도메인/스크립트 URL 거절, `no-referrer` |
| 결제 복귀 | 파일 재업로드 없이 주문 상태 확인 | 복귀 주소의 주문번호는 조회 힌트. `success`·토큰·금액·회원ID는 지급 근거가 아님. 복귀 표시만 있고 보관 주문이 없으면 새 주문으로 넘어가지 않음 |
| 완료 확인 | 서버 주문을 확인한 뒤 사용자가 결제 결과 확인 | 자동 승인/폴링 없음. 신뢰된 서버 상태와 원장에 따라 지급 여부 표시 |
| 응답 유실·새로고침 | 같은 계정의 보관 주문을 다시 조회 | 새 번호로 자동 주문/승인하지 않음. 이미 지급된 주문은 읽기로 복구 |
| 로그아웃·다른 계정 | 주문과 결제 링크를 즉시 화면에서 제거 | 진행 중 요청 중단·늦은 응답 폐기. 다른 계정의 복귀 번호는 서버 소유권 검사에서 거절 |

브라우저 `sessionStorage`에는 **계정별 최근 주문번호 한 개**만 보관한다. 토큰·결제창 URL·금액·원본 리플레이·구매 동의는 저장하지 않는다. 탭의 저장소가 유지되는 동안 새로고침/다른 사이트 이동 후 같은 번호를 확인할 수 있지만, 탭을 닫거나 브라우저 저장소를 삭제하면 복구가 보장되지 않는다. 전체 구매 내역 화면이나 장기 기록을 대신하지 않는다. 주문번호 보관이 실패하면 신규 주문/결제 진행 요청 전에 멈추며, 이미 알려진 복귀 주문의 읽기는 가능하다. 미확정 주문에서 새 주문으로 자동 넘어가지 않는다. 시작 전 취소 또는 지급 완료 후에만 새 주문 준비를 허용한다.

UI는 서버가 확인한 구매 조건을 표시하며 임의 응답을 HTML로 렌더링하지 않는다. 지급 완료는 해당 주문의 지급 이력이며 현재 50회가 남았다는 뜻이 아니다. 환불/사용 이후 잔액은 AI 분석 화면의 잔액 조회로 별도 확인한다. 미리보기 체크박스는 최종 판매 동의·미성년자 절차를 구현한 것이 아니다. 확정된 정책과 동의 증적 처리는 판매 전에 별도로 연결해야 한다.

클라이언트 요청/응답은 최대 2KB/4KB, 고정 로컬 경로만 사용하고 토큰은 요청 헤더에만 전달한다. 쿠키·자동 재시도·백그라운드 상태 조회·새 분석 로그를 추가하지 않았다. 실제 브라우저에서 모바일 390px/데스크톱 1280px, 파일 없는 복귀, 새로고침, 계정 전환, 외부 도메인 차단, 생성/지급 응답 유실 복구, 저장소 차단을 확인했다. 기존 무료 분석과 AI 미리보기 회귀 검사도 유지한다.

## 공개 상품 초안과 격리된 심사용 TEST 경로

2026-10-26 사용자 승인 초안은 **AI 분석 50회 / 3,300원(부가세 포함) / 결제 완료일부터 365일**이다. 월 구독·자동 갱신이 아닌 횟수권이다. `/ai-replay-pass/`에 로그인 없는 상품 안내, 무료/유료 비교, 제공 방식·조건부 환불 초안과 심사용 TEST 화면을 준비했다. 푸터에서 연결한다. **로컬 구현·검증 상태이며 아직 공개 배포·서버 활성화·실제 판매·재신청은 하지 않았다.**

### 안내와 구현의 경계

- 지급 기한 ‘결제 완료 후 1영업일 이내’, 이용 기간 내 미사용분 환불(정상 제공 1회당 66원 공제), 판매자 귀책 문의 기간·환급 처리 기준은 상품 페이지의 **추가 판매 조건 초안**이다. 사용자에게 최종 확인하고 운영 절차를 연결해야 한다. 50회·3,300원·365일 초안 승인이 이 모든 조건의 확정이나 실제 판매 승인은 아니다.
- 실제 판매는 동일 로그인 계정의 횟수 지급 → 웹에서 JSON/선수 선택 → 결과 웹 열람 방식으로 준비한다. 현재 심사용 TEST는 이 실제 지급·AI 분석을 실행하지 않는다. 이메일·PDF 전송 상품으로 안내하지 않는다.
- 일일 정상 완료 5회·시도 10회 기준으로 50회는 최소 10일이 필요하다. AI가 알 수 없는 시야·음성·의도와 승률 보장의 한계를 고지했다.
- 운영 원장의 기존 expiresAt 절대 시각/null 정책에 구매 완료일부터 365일을 계산해 적용하는 변경은 **아직 미연결**이다. TEST의 demoExpiresAt은 승인 상태를 관측해 시연 확정한 시각 +365일이며, 운영 이용권 만료·토스의 실제 결제 시각 증명이 아니다. 장기 결과 보관/구매 내역·최종 동의 절차도 별도다.
- 환불의 7일 고지로 소비자의 더 긴 법정 권리를 제한하지 않는다. 미사용분 계산 예시는 10회 정상 이용 후 40회 ×66원 =2,640원이다. 판매자 귀책 미제공분은 정상 사용분에서 제외한다. 유효한 디지털 콘텐츠·서비스 청약철회 환급 기산일은 ‘운영자 확인 완료일’로 늦추지 않는다. 공식 [전자상거래법 제17조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031805915), [청약철회·환급 안내](https://easylaw.go.kr/CSP/CnpClsMainBtr.laf?ccfNo=4&cciNo=1&cnpClsNo=2&csmSeq=835)를 참고했다. 최종 약관·부분 제공 동의·환불 운영 검증을 대신하지 않는다.

5. 정식 판매는 가맹 승인, LIVE 제공자/정산·현금영수증, 계정 지급·상대 만료·오류 보상/환불·복구/콜백·최종 동의까지 검증한 후 별도 활성화. 공식 [테스트→운영 전환 안내](https://docs-pay.toss.im/tutorial/step-6)를 따른다.

### 검증 기록

합성 제공자 + 메모리 DB 단위 검사에서 TEST/LIVE·다른 세션·잘못된 URL/가격/거래·환불 증명·일일/누적 제한, 동시 생성/승인 1회, 트랜잭션 재시도, 생성/승인 응답 유실과 승인 후 DB 장애 복구를 검사했다. 실제 Firestore Emulator에서는 동시 전송권·복구·운영 원장 미생성 및 비로그인/회원/관리자 클라이언트의 직접 읽기/쓰기 차단을 확인했다. 브라우저에서는 모바일/데스크톱·라이트/다크, 공개 안내의 결제 API 미호출, 외부 이동/복귀·코드 재입력·저장소 차단·유실 복구를 확인했다. 모든 토스 도메인 요청은 로컬로 가로채고 다른 외부 요청은 차단했다. 실제 거래·유료 AI 품질·실제 가맹 심사 통과를 증명하는 테스트는 아니다.

## 심사용 TEST 공개 배포 (2026-10-26)

위 ‘로컬 준비’ 기록 이후 사용자 승인으로 상품 페이지와 전용 TEST 서버를 별도로 배포했다. **실제 판매·가맹 재접수·LIVE 키·유료 AI·운영 이용권 지급은 여전히 미활성**이다. [공개 상품 초안](https://trackingsa.com/ai-replay-pass/)은 로그인 없이 확인할 수 있고, TEST 진행에는 별도로 전달하는 심사용 접근코드가 필요하다. 기존 무료 분석·후원 링크와 운영 Firebase/App Check 공개 설정을 보존했다.

- Firebase에는 Node.js22·256MiB·최소0/최대1 인스턴스·60초의 replayPurchaseTest만 추가했다. TEST Secret 두 개만 바인딩하며 다른 함수·Firestore/Storage 규칙은 배포하지 않았다. 실제 배포 중인 Firestore의 기본 거절 규칙으로도 TEST 문서의 비로그인/회원/관리자 직접 접근이 차단됨을 Emulator에서 확인했다.
- Secret Manager 활성화와 두 TEST 비밀값 저장은 사용자가 명시적으로 승인했다. 새 코드의 로컬 복구용 사본은 Windows DPAPI로 암호화하며 공개 소스·URL·로그에는 넣지 않는다. 이번 검증은 공식 공용 TEST 키를 사용하며 실제 가맹점 LIVE 승인을 의미하지 않는다.
- 기존 잠금 파일의 body-parser를1.20.8에서 호환 패치1.20.9로 갱신했다. [공식 보안 공지](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828)의 압축 본문 뒤 잔여 바이트 처리 문제에 대응한 변경이다. 직접 의존성은 추가하지 않았으며 새 설치 audit0건과 로컬 HTTP 서버의 잘못된 압축 요청 거절·프로세스 생존을 확인했다.
- 첫 실제 브리지 요청에서 Node와 Cloudflare의 Fetch 차이를 확인했다. workerd는 redirect:error를 지원하지 않아 요청 생성 단계에서 중단됐다. [공식 Request 문서](https://developers.cloudflare.com/workers/runtime-apis/request/)에 맞춰 manual을 사용하고 모든3xx를 거절한다. 인증 헤더를 새 주소에 전달하지 않으며 자동 따라가기·재시도도 하지 않는다. 실제 workerd 로컬 검사에서 정상 전달/리다이렉트 차단을 합성 응답으로 검증했다.
