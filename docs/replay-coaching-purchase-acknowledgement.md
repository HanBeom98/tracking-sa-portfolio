# 구매 조건 확인 기록·문구 버전 보존

2026-10-27. **로컬 개발 미리보기용 확인 기록**을 구현했다. 현재 확인 문구는 `purpose: preview`이며 실제 판매 약관 동의나 사업자의 미확정 환불 조건 승인으로 취급하지 않는다. 공개 TEST·운영 결제·유료 AI·가맹 재접수는 이번 작업에서 변경하지 않았다.

## 기록하는 내용

| 항목 | 기준 |
|---|---|
| 구매 조건 | 기존 주문의 가격·횟수·이용 기간·`termsVersion` 보관 |
| 확인 문구 | 화면에 표시한 제목·본문·문구 버전·`preview` 구분 보관 |
| 내용 지문 | 문구와 구매 조건을 함께 계산한 SHA-256 값. 가격·횟수·기간 변경도 구분 |
| 서버 확인 시각 | 인증된 주문 생성 처리 시 서버가 기록한 `acceptedAt`. 최초 `createdAt`과 동일 |
| 소유자 | 기존 주문의 인증 UID 기반 비공개 경로와 소유자 검증 사용 |

기존 주문 문서에 한 번에 기록한다. 새 동의 컬렉션이나 IP·기기 지문 수집을 추가하지 않았다. 서버 시각은 주문 접수 처리 시각이며 사람이 실제로 문구를 읽은 순간을 측정한 값이 아니다. 내용 지문도 전자서명·공인 시각 인증이 아니며 그 자체로 법적 입증의 충분성을 보장하지 않는다.

## 화면·API 동작

1. 상품 조회가 현재 서버의 확인 문구와 버전·지문을 반환한다. UI는 본문을 생략하지 않고 체크박스 앞에 표시한다.
2. 사용자가 확인 항목을 선택한 뒤 주문을 요청한다. HTTP 생성 요청에는 기존 `termsVersion`과 `acknowledgement: {accepted: true, version, digest}`가 필요하다.
3. 서버는 현재 문구·조건과 대조한다. 미확인·클라이언트 시각/본문 삽입·이전 조건의 지문을 거절하며 그 경우 주문을 쓰지 않는다.
4. 주문과 확인 기록을 같은 트랜잭션에 저장한다. 동시 요청이나 응답 유실 뒤 재시도에도 최초 문구·시각을 유지한다.
5. 조건 변경 응답을 받으면 UI는 이전 상품과 체크 상태를 지운다. 상품을 다시 읽고 새로 확인해야 한다.

주문 조회에는 당시 문구를 반환한다. 구매 내역의 각 행에는 문구 버전·서버 시각만 반환하여 본문을 10번 전송하지 않는다. 비공개 결제 바인딩도 문구 전문 대신 작은 확인 식별 정보만 보관하고 기존 구매 조건과 함께 대조한다.

확인 기록이 없는 이전 형식 주문은 조회·기존 처리 호환을 유지하며 ‘확인 기록 없음’으로 표시한다. 새 생성 요청을 재시도했다는 이유로 과거 동의를 만들어 넣지 않는다. 결제·만료 계산·환불 예약도 확인 기록을 갱신하지 않는다. 운영 전환 시 이전 형식 미결제 주문의 진행 기준은 별도로 정해야 한다.

## 실제 판매 전 남은 연결

현재 문구는 ‘실제 결제 약관 동의가 아니다’라고 명시한다. 승인된 실제 판매 조건을 버전 문서로 준비하고 그 문서에 대한 실제 구매 확인 절차를 연결해야 한다. 초안에서 제안한 지급 기한·추가 미사용분 환불·보관·미성년자 조건을 이번 개발 확인으로 확정하지 않는다.

LIVE 제공자·운영 인증 API·실제 계정 AI 지급/차감·환불 운영·가맹 승인도 남아 있다. 3,300원·50회·365일의 기존 방향과 과거 구매 조건 보존은 유지한다. [조건 제안](replay-coaching-sales-conditions.md), [구매 내역](replay-coaching-purchase-history.md), [재심사 체크리스트](tosspay-reapplication-checklist.md)를 함께 본다. 배포·실제 판매·재접수·외부 문의 발송은 하지 않았다.
