# AI 분석 횟수권: 구매 잔액·주문·환불·비용 분리

2026-10-26. 월간 AI 구독 제안 대신 **한 번 구매한 횟수에서 정상 해설마다 1회를 사용하는 상품**으로 개발 방향을 변경했다. 기본 리플레이 분석은 무료다. 실제 상품 가격/제공 횟수·유효기간·환불 약관 확정, 실제 결제 연결, 판매 활성화와 운영 배포는 아직 진행하지 않았다. 개발 예시는 3,300원/50회이며 실제 상품 설정의 기본값이 아니다. 사용자는 사업자등록 및 통신판매업 신고를 이미 완료했으며, 토스페이 가맹 신청에서 **조건부 환불**을 선택해 신청했다고 확인했다. 가맹 승인·계약 조건·운영 결제 수단은 아직 확인하지 않았다.

## 현재 구현과 운영 경계

- 토스페이 공식 TEST API로 승인·660원 부분환불·나머지 2,640원 환불(최종 잔액 0원)과 동일 환불의 멱등 처리를 확인했다. TEST 전용 서버 클라이언트·원장 증명 검증 포트를 추가했으며 실제 응답 차이도 회귀 검사에 반영했다. 운영 지급·실거래·콜백·판매 화면 연결은 아직 없다. 상세 범위는 [토스페이 연결 준비](replay-coaching-tosspay.md)를 따른다.

- 비활성 `replayCoachingReview` API가 새 횟수권 잔액을 사용한다. 기존 월간 `subscription.replayCoaching`나 일반 유료 회원/관리자 역할은 횟수권이 아니다.
- `createCreditOrderManager`는 신뢰된 서버 작업용이며 기본 비활성이다. HTTP/관리자 버튼/운영 계좌·키·은행 연결은 없다. 결제/환불 검증 의존성은 확인만 하며 돈을 송금하지 않는다. 브라우저의 입금 주장·스크린샷·구독 필드로 지급하지 않는다.
- 로컬 `?coaching=review&transport=api`에서 잔여 횟수 표시와 새 API 응답을 검증했다. 여기에 구매 조건·조건부 환불 안내 미리보기를 추가했다. 일반 사이트에는 구매 버튼/새 결제 경로를 추가하지 않았고 유료 기능을 활성화하지 않았다.
- 이전 월간 모의/소액 품질 시험 경로와 기록은 보존한다. 새 잔액으로 자동 이관하거나 기존 비용을 초기화하지 않는다. 기존 월간 장부를 새 횟수권으로 인정하지 않는다.

## 데이터와 정합성

기존 서버 전용 `_replay_coaching_users` 아래 문서/하위 컬렉션을 사용한다. 기존 규칙이 소유자·사이트 관리자 클라이언트의 읽기/쓰기를 모두 막는다. Auth 토큰으로 검증한 UID만 서버 경로를 결정한다. 규칙 변경·새 인덱스·조회/스캔은 없다.

| 기록 | 역할 |
|---|---|
| `credits_v1_<UID해시>` | 누적 구매/사용/환불·사용 가능/분석 예약/환불 예약과 남은 주문 목록 |
| 위 문서의 `orders/<주문번호>` | 서버가 고정한 가격·횟수·약관 버전·만료 정책, 결제 해시와 주문별 잔여/사용/환불 수량 |
| `requests/<요청번호>` | 별도 문서의 중복 차감 방지 영수증·예약/정산·정상 해설. 지난 두 기간만으로 조회 범위를 제한하지 않음 |
| `refunds/<환불번호>` | 환불 수량·금액·대기/확정과 환불 거래 해시 |
| `credit_payment_<거래해시>`, `credit_refund_<거래해시>` | 하나의 외부 거래를 여러 주문/계정/환불에 중복 적용하지 못하도록 하는 공용 표식 |
| `credit_cost_<통화계약>_<UID해시>_<한국월>` | 이용자의 월별 제공자 비용·일별 성공/시도 수. 구매 잔액과 별개 |
| 기존 `_replay_coaching_months` | 기존 내부 시험과 공유하는 월별 전체 비용/예약/생성 횟수와 중단 제어 |

은행 계좌번호·입금자명·원본 리플레이·닉네임·좌표를 새 기록에 저장하지 않는다. 결제/환불 참조는 해시로 남긴다. 사용자 문서의 구독 필드를 수정하지 않는다.

`누적 구매 = 누적 사용 + 누적 환불 + 남은 수량 + 분석 예약 + 환불 예약`을 검사한다. 주문별 수량과 남은 주문 목록도 일치해야 한다. 한 계정에 분석은 한 건만 처리한다. 잔여/예약이 있는 주문은 최대 50개, 전체 잔여/예약 안전 상한은 10,000회다. 한 주문은 최대 50회다. 한도를 넘으면 기존 구매 기록을 지우는 대신 거절한다. 사용/환불이 끝난 주문은 잔액 문서의 목록에서만 제거하고 별도 주문/요청 영수증은 보존한다. 향후 판매 화면에서는 결제 전 용량 확인과 지급 불가 입금의 처리 절차가 필요하다.

## 구매와 추가 구매

1. 서버의 명시적 상품 설정으로 주문을 만든다. 가격/횟수/약관 버전/유효기간을 구매자 입력으로 받지 않는다. 현재 균일 단가 상품만 지원한다.
2. 신뢰된 검증기가 실제 결제 원장에서 주문·회원·금액·KRW·고유 거래번호와 입금 완료를 확인해야 한다. 검증 호출은 DB 트랜잭션 밖에서 수행한다. 실제 은행 검증기는 미연결이며 시험에서는 대역을 사용한다.
3. 트랜잭션에서 주문·거래 중복 표식·잔액을 함께 기록한다. 같은 확인을 반복하거나 동시에 수행해도 한 번만 지급한다. 같은 입금으로 다른 계정/주문을 지급하지 못한다.
4. 추가 구매는 새 주문 수량만 더한다. 기존 사용량/결과/비용을 초기화하지 않는다. 환불한 주문의 결제 확인을 다시 해도 재지급하지 않는다.

자동결제·월별 잔액 리셋·자동 갱신은 없다. 추가 구매한 100회 중 같은 달에 51회를 정상 사용해도 월 구독의 50회 제한으로 거절하지 않는 것을 검사했다. 다만 아래의 별도 처리/비용 안전 한도는 유지한다.

## 사용과 제공자 비용

새 요청은 잔액/중복/전역 제어/일별 한도 확인 → 기존 정확한 입력 계수와 비용 견적 → 횟수 1회와 최대 비용 동시 예약 → 전송 직전 권한/만료/중단/견적 재확인 → 단일 생성 → 원자적 정산 순서다. DB 재시도 안에서 제공자를 호출하지 않는다. 프롬프트·모델·토큰 가격 계약은 변경하지 않았다.

| 결과 | 구매 횟수 | 제공자 비용 |
|---|---|---|
| 검증된 새 해설 | 1회 확정 사용 | 확인된 실제 사용량 정산 |
| 기존 완료 요청/보관 결과 조회 | 추가 사용 없음 | 계수/생성 없음 |
| 알려진 실패·사용 불가능한 결과 | 예약한 횟수 반환 | 발생한 비용은 보존 |
| 전송 전 중단/만료/계정 차단 | 횟수 반환 | 0 |
| 전송/사용량/정산 여부 미확정 | 예약 유지, 자동 재시도 없음 | 신뢰된 명시적 복구 전까지 비용 예약 유지 |
| 신뢰된 복구로 불명확한 요청 종료 | 고객 횟수 반환 | 최대 견적 비용 보존, 늦은 정산 차단 |

월이 바뀌어도 잔여 횟수는 사라지거나 다시 지급되지 않는다. 월별 전역/개인 마이크로달러 예산과 전체 처리 한도는 별도다. 기존 일별 정상 5회/시도 10회 제한도 유지한다. 추가 구매로 비용/일별 한도를 우회하지 못하며, 제한에 걸려도 구매 잔액은 없애지 않는다. 운영 판매 시 이런 제한을 고지하고 수요/무료 인프라 용량과 함께 조정해야 한다.

응답은 `{mode, requestId, outcome, credits:{remaining,held}, result}`다. 잔여 수량은 현재 유효하며 예약되지 않은 수량이다. `held`는 AI 분석 예약이며 환불 예약 수량은 포함하지 않는다. 내부 구매/환불 원장·비용·제공자 ID는 반환하지 않는다. 잔액 소진·주문 만료·생성 중단·잔액 계정 차단 뒤에도 검증된 로그인 계정이 소유한 완료 해설은 조회할 수 있다. 보관의 영구성을 약속하지 않는다.

## 화면과 재요청

### 구매 조건과 조건부 환불 미리보기

`ui/replay-credit-purchase.js`는 정확히 `http://127.0.0.1:4173`의 `?coaching=review&transport=api`에서만 표시한다. 일반 무료 분석은 이 모듈을 불러오지 않는다. 무료 기본 분석/유료 AI 해설의 차이, 개발 예시 3,300원/50회(미확정), 단건 구매·자동 갱신 없음, 현재 일별 정상 5회/시도 10회 제한, 처리/비용 제한, 분석의 한계, 미확정 유효기간·결과 보관 기간을 함께 안내한다.

조건부 환불 안내는 전체 미사용/일부 사용/정상 제공/오류·미제공을 구분한다. 미사용분의 부분환불과 법정 소비자 권리를 표시하며, 구체적인 기간·신청 방법·금액 산정 및 미성년자 구매 절차는 판매 전 확정 대상으로 명시한다. 이는 판매 약관이나 환불 접수 기능이 아니다. 토스페이 신청 화면의 선택만으로 환불 정책 구현·가맹 승인이 완료됐다고 취급하지 않는다.

안내는 버튼으로 펼치고 접으며 키보드 포커스를 유지한다. 로그아웃/계정 변경 시 안내를 접고 로그인 표시를 갱신한다. 분석 대상 변경 시 기존 화면과 이벤트를 정리한다. 결제 버튼은 항상 비활성이고 로그인이나 URL 플래그로 해제하지 않는다. 화면을 조작해도 결제 SDK·외부 호출·주문 생성·동의 기록·추가 DB 읽기/쓰기·잔액 지급은 없다. 확정 약관이 없는 상태에서 법적 동의를 받는 체크박스도 추가하지 않는다.

실제 구매 화면을 열려면 서버 상품/약관/유효기간·보관 기간·판매자 표시, 미성년자·환불 예외 처리, 결제 전 잔액 용량 확인, 토스페이 서버 검증·취소 연동, 중복 지급 방지까지 연결해야 한다. 프런트엔드 버튼 활성화만으로 판매를 시작하지 않는다.

### 해설 요청과 결과 조회

화면은 구독 상태 대신 사용 가능한 잔여 횟수/처리 중 횟수를 표시한다. 응답 해시와 현재 분석 근거·참조를 확인하고 문자열을 이스케이프한다. 로그아웃/계정/분석 대상 변경 때 카드와 잔액 표시를 지우며 늦은 응답을 버린다.

페이지 메모리에 계정·수치 근거·요청 번호를 최대 210개 보관한다. 결과/토큰을 영구 저장하지 않는다. 응답 유실·처리 중·정산 미확정은 같은 번호의 `result`만 수동 조회한다. 조회 실패/404에서 생성으로 자동 전환하지 않는다. 서버가 잔액 부족/미구매/로그인/한도 등 **생성 전 거절을 명확히 반환한 경우에만** 추가 구매/로그인 등의 조치 후 같은 번호로 수동 생성 재시도를 허용한다. 중복 클릭/동시 화면도 번호를 공유한다. 새로고침/새 탭 후 요청 복구와 동일 수치 근거의 경기/선수 구별은 여전히 별도 운영 과제다.

## 만료와 환불

유효기간은 확정하지 않았다. 서버 상품 설정에 `expiresAt`을 반드시 명시해야 하며, 명시적 `null`(만료 없음) 또는 절대 만료 시각만 허용한다. 설정 누락으로 무기한 상품을 판매하지 않는다. 구매 당시 정책은 주문에 고정한다. 예제의 `test_terms_only`/`emulator_only`는 판매 약관이 아니다. 소멸 기간이나 구체적인 환불 약관을 공개/적용하지 않았다.

만료된 미사용 수량은 사용 대상에서 제외하되 회계 수량을 삭제하거나 자동 환불하지 않는다. 다른 유효 주문의 횟수는 계속 사용할 수 있다. 사용 시 만료가 빠른 주문부터 사용하고, 동률은 주문 번호 순이다.

환불은 먼저 주문의 미사용 수량을 잠가 사용 가능 잔액에서 제외한다. 해당 주문에서 AI가 처리 중이면 환불 예약을 거절한다. 실제 환불 완료·회원/주문/원래 결제/환불 번호/금액을 검증한 뒤 잠긴 수량을 환불로 확정한다. 확인이 불명확하면 잠금을 유지하며 자동 해제하지 않는다. 동일 환불 확인은 한 번만 적용하고, 같은 외부 환불 거래를 다른 환불에 재사용하지 못한다. 이미 제공한 해설을 삭제하지 않는다.

현재 내부 계산은 균일한 원 단가 × 환불 수량이다(예: 3,300원/50회라면 회당 66원). 할인/프로모션·사용한 서비스 하자에 대한 환불/보상·환불 거절·은행 환불 예약 취소 등 예외 운영은 미구현이다. 이 수량 잠금/확정 도구가 법적 환불 정책이나 모든 환불 의무를 대신하지 않는다. [전자상거래법 제17조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1027063323)의 미제공 부분 청약철회 등을 반영해 약관/실제 절차를 정해야 한다.

## 무료 티어 영향과 검증

미배포이므로 운영 DB 작업/과금은 추가하지 않았다. 새 유료 의존성·스케줄·폴링·유료 TTL·분석 로그는 없다. 같은 Firestore 안에서 정확한 차감·주문/환불 추적을 위해 기록을 세분화했다. 정상 새 해설은 경합 없는 메모리 검사에서 **22읽기/12쓰기**, 완료 생성 중복은 **5읽기/0쓰기**, 명시적 결과 조회는 **2읽기/0쓰기**다. Auth 검사·DB 트랜잭션 재시도·기존 사이트 사용량은 제외한다. 정상 생성 100건이면 이 경로만 2,200읽기/1,200쓰기다.

장기 횟수권은 주문/환불/요청 기록이 누적된다. 결과/중복 차감 방지 기록을 무작정 지우거나 월별로 초기화하지 않는다. 이 저장량 증가와 읽기/쓰기 무료 한도는 운영 활성화 전 실제 전체 사용량과 함께 확인해야 한다. 비용이 항상 0원이라고 보장하지 않는다. 운영 보관/삭제 정책도 별도로 정해야 한다.

- 주문/환불 검사 9개: 지급 중복·금액/계정/입금 불일치·추가 구매·부분/전체 환불·환불 중 사용 경합·거래 재사용·만료/용량.
- 횟수/비용 검사 8개: 월 경계·같은 달 51회·만료 순서·전송 전 취소·정산 재시도·미확정 복구·마지막 1회 동시 사용·오염 장부.
- API/화면 단위 및 브라우저: 소유자·입금 주장 주입 차단·잔액 표시·추가 구매 후 재시도·응답 유실 조회·로그아웃/늦은 응답·기본 무료 경로.
- 구매 안내 브라우저: 390/1280px 표시·일별 제한/조건부 환불/미확정 정책 고지·키보드 접기와 포커스 복귀·로그아웃/계정 변경·분석 대상 변경 정리·운영 origin 거부·결제/해설 요청 0건·로그인 후에도 결제 비활성.
- Firestore Emulator: 기존 규칙에서 개인 원장/하위 기록 접근 차단, 실제 트랜잭션의 중복 지급/환불·마지막 1회 환불/사용 경합·미확정 비용 복구 확인. 은행/PG/Auth 검증기·AI 제공자는 대역이다. 운영 DB·실제 돈·새 유료 AI 호출 없이 검증한다.
