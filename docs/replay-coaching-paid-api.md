# 유료 AI 해설 API의 인증·횟수권·결과 소유권

2026-10-26. 월 구독 제안에서 구매한 분석 횟수권으로 변경했다. 현재 결제/잔액/비용 계약의 기준 문서는 [AI 분석 횟수권](replay-coaching-credits.md)이다. 운영 비활성·미배포이며 실제 입금 확인·환불·유료 AI 호출·운영 DB 변경은 하지 않았다. 기존 무료 리플레이 분석은 유지한다.

## 운영 경계

`createReplayReviewHandler`와 Firebase `replayCoachingReview` 진입점은 기본 비활성이다. 실제 제공자·계수기·운영 비밀 키/한도는 연결하지 않았다. 환경 변수에 키가 있다는 이유로 활성화하지 않으며 배포 workflow 대상에도 추가하지 않았다. 기존 `replayCoachingPreview`와 월간 비용/권한 시험 경로는 별도의 내부 모의/이전 시험 경로로 남긴다.

새 해설은 프로필 구독 필드 대신 신뢰된 서버가 입금을 확인해 기록한 개인 횟수권 잔액으로 승인한다. `subscription.status=active`, 관리자 역할, 이전 `replay_ai_monthly_v1` 기록만으로 횟수권이 생기지 않는다. 구매/환불 관리 함수도 기본 비활성인 내부 함수이며 HTTP/사이트 관리자 클라이언트에 노출하지 않았다. 실제 운영자 입금 확인 도구·은행 대사/증빙 검증 포트와 판매 화면은 후속 작업이다.

## 요청과 응답

서버는 `verifyIdToken(token, true)`로 확인한 UID만 사용한다. POST 본문은 정확히 `{action, requestId, evidence}`이고 `action`은 `generate` 또는 `result`다. UID·역할·주문·가격·잔액·결제 완료 주장·모델 결과를 받지 않는다. 본문 24KB와 기존 v2 후보/사건 창 입력 검증을 적용한다. CORS는 `https://trackingsa.com`, 응답은 `no-store`다.

| 요청 | 처리 |
|---|---|
| 새 `generate` | 구매 잔액/비용 한도 확인 → 계수/견적 → 횟수와 비용 동시 예약 → 전송 직전 검사 → 한 번 생성/정산 → 표시용 DTO |
| 완료된 같은 `generate` | 같은 UID·요청 번호·근거의 저장 결과 반환. 추가 계수·생성·쓰기 없음 |
| `result` | UID가 정한 개인 요청 문서만 조회. 없더라도 생성으로 전환하지 않음 |

성공 응답은 `{mode:'review', requestId, outcome, credits:{remaining,held}, result}`다. 예전 월간 `used` 숫자를 반환하지 않는다. 서버가 기존 검증/정규 렌더링을 통과한 결과만 표시용 DTO로 투영하며, 제공자 ID·견적·비용·내부 선택·구매 원장은 노출하지 않는다. 클라이언트는 요청 번호/구조/잔액 범위와 근거 해시/카드 참조를 재검증한다. 해시는 경기/선수의 실재성·원본 진위를 인증하지 않는다.

정상 해설은 1회 사용하고 알려진 실패는 횟수를 돌려준다. 제공자 비용은 실제 발생분을 보존한다. 불명확한 전송/정산은 횟수/비용 예약을 유지하며 신뢰된 복구 전 자동 재시도하지 않는다. 추가 구매로 기존 사용량이나 월 비용을 리셋하지 않는다. 전체/개인 비용, 일별 5회 정상/10회 시도 제한은 별도로 유지한다.

본인 완료 결과는 잔액 소진·구매 만료·생성 중단 뒤에도 추가 차감 없이 조회할 수 있다. 미사용분 환불이 이미 제공한 결과를 삭제하지 않는다. 다른 UID가 같은 요청 번호를 알아도 그 계정의 결과는 조회할 수 없다. 이전 월간 장부는 보존하지만 새 API의 구매 잔액/영수증으로 자동 이관하지 않는다.

## 로컬 화면

`http://127.0.0.1:4173/stats/sudden-attack/replay/?coaching=review&transport=api`에서만 새 HTTP 클라이언트/컨트롤을 불러온다. 기본 무료 분석 및 저장 해설 파일을 읽는 `?coaching=review` 화면은 유지한다. 기본 정적 로컬 서버에는 API가 없고, 자동 검증의 Playwright 경로 어댑터가 실제 서버 핸들러를 연결한다. 운영 origin 제한을 loopback으로 확장하지 않는다.

버튼 클릭 후 현재 Firebase 사용자의 토큰을 받아 고정 loopback 경로에만 보낸다. 외부 URL 설정·쿠키·리다이렉트·폴링·자동 재시도·토큰/결과의 로컬 저장소 저장은 없다. 실제 응답 스트림 12KB와 JSON/UTF8을 검사한다. 65초 클라이언트 제한/화면 닫기/로그아웃은 서버 작업 취소를 뜻하지 않는다.

요청 번호는 같은 페이지에서 계정·수치 근거별 최대 210개를 보관한다. 결과가 불명확하면 같은 번호로 저장 결과만 수동 조회한다. 잔액 부족 등 생성 전 거절이 명확하면 추가 구매 등의 조치 후 같은 번호로 수동 생성 재시도를 허용한다. 성공/미확정 요청에 새 번호를 자동 발급하지 않는다. 페이지 새로고침/새 탭 후 복구, 장기 결과 보관/삭제·동일 수치 근거의 다른 경기 구별은 별도 운영 과제다. 로그아웃·계정/분석 대상 변경 시 카드/잔액을 지우고 늦은 응답을 버린다.

## 비용과 검증 범위

현재 기록은 기존 서버 전용 Firestore 컬렉션 아래에 있으며 사용자/사이트 관리자 클라이언트가 읽거나 수정할 수 없다. 주문/횟수권/중복 차감 방지 기록을 분리하며 신규 생성은 경합 없는 검사에서 22읽기/12쓰기, 완료 생성 중복 5읽기/0쓰기, 결과 조회 2읽기/0쓰기다. Auth 폐기 검사·DB 재시도·사이트 전체 사용량은 별도다. 장기 요청/주문 기록이 누적되므로 운영 활성화 전 실제 무료 한도와 보관 정책을 확인해야 한다. 새 유료 의존성·스케줄·TTL·분석 수집은 없다.

단위·브라우저·Firestore Emulator에서 중복 지급/차감·추가 구매·환불 예약/확정·소유권·월 경계·미확정 비용 복구를 검증한다. 토큰 검증/계수/생성/은행 확인은 대역이며 실제 결제·Auth 네트워크·AI 제공자 연결을 검증한 것은 아니다. 최종 판매 조건과 은행 확인/환불 운영 도구를 완성하기 전에는 유료 공개하지 않는다.
