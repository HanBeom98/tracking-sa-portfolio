# 모의 해설 정산 분리와 미확정 예약 복구

2026-10-25. 실제 모델을 연결하기 전의 로컬 검증 단계다. 운영 미배포·기본 비활성을 유지하며 공급자 키·유료 호출·결제·구독 권한은 추가하지 않았다. 아래 기존 모의 HTTP 경로의 `units`는 **테스트 비용 단위**다. 후속 [통화 준비 경로](replay-coaching-budget.md)는 문서 키·표식을 분리하고 마이크로달러·단가·usage 검사를 적용한다. 실제 청구는 미연결이다.

## 변경 이유와 결과

기존에는 `finishCoachingQuota(..., success)` 하나로 사용자 성공 횟수와 비용 단위를 함께 확정/해제했다. 모의 생성에는 실제 비용이 없지만, 유료 모델에서 잘못된 문장이 나왔다는 이유로 비용까지 해제하면 이미 발생한 공급자 비용이 장부에서 사라진다.

이제 `finishCoachingQuota(..., { customerSuccess, chargedUnits })`로 두 값을 분리한다. 공급자 비용을 5단위 예약하고 실제 사용을 3단위로 확인한 상황을 가정하면 다음과 같다.

| 결과 | 사용자 성공 횟수 | 확정 비용 | 해제되는 비용 예약 |
| --- | ---: | ---: | ---: |
| 정상 해설 | +1 | +3 | 2 |
| 해설 검증 실패 | +0 | +3 | 2 |
| 전송 전 중단 확정 | +0 | +0 | 5 |
| 전송 후 결과 불명 | 확정하지 않고 1회 예약 유지 | 5단위 예약 유지 | 0 |
| 미확정 작업을 보수적으로 종료 | +0, 사용자 예약 해제 | 최대액 +5 | 0 |

`chargedUnits`는 서버의 신뢰할 수 있는 실행 결과에서만 정하는 값이다. 브라우저 요청에는 이 필드나 성공 여부를 받지 않는다. 음수·소수·예약액 초과·성공 여부 타입 오류는 정산을 거절하고 예약을 유지한다. 후속 [비용 준비](replay-coaching-budget.md)와 [공급자·결과 복구](replay-coaching-provider.md)에서 usage/요금 해석과 결과의 원자적 보관을 내부 구현했고 실제 소액 생성의 로컬 정산도 확인했다. 청구서 대조는 미실행이며 의미 품질 개선이 남아 있다.

## 처리 단계

1. **reserved**: 사용자 1회와 전역 비용 최대액을 트랜잭션으로 함께 예약한다.
2. **dispatching**: 생성을 시작하기 전에 전송 시작 상태를 별도 트랜잭션으로 기록한다. 이 저장 결과를 확인하지 못하면 생성을 호출하지 않는다.
3. **completed / failed**: 생성과 검증 결과를 받은 뒤 성공 횟수와 확인된 비용을 한 번에 정산한다.
4. 실행/저장 결과가 불명확하면 예약 상태를 유지한다. 시간이 지났다는 이유로 자동 해제하거나 재생성하지 않는다.

전송 시작 상태 기록은 한 방향 전환이다. 같은 예약에 두 번 기록하려 하면 거절한다. 따라서 저장 응답 유실을 이유로 같은 작업을 다시 생성하는 경로가 없다.

현재 모의 API의 실행 규칙은 다음과 같다. 성공 응답 형식과 브라우저 동작은 유지한다.

| 모의 실행 결과 | 비용 정산 |
| --- | --- |
| 로컬 문장 생성 자체가 예외로 중단 | 실제 외부 호출이 없으므로 0단위로 정산 |
| 문장은 반환됐으나 형식/근거 검증 실패 | 발생한 비용을 흉내 내 예약 단위 전액 정산. 사용자 성공 횟수는 증가하지 않음 |
| 정상 응답 | 예약 단위 전액을 모의 비용으로 정산하고 사용자 성공 횟수 +1 |

이 예외 처리의 0단위 규칙을 미래의 공급자 타임아웃/5xx에 적용하면 안 된다. 공급자 모드를 추가할 때는 확인된 usage와 미확정 비용을 별도로 전달해야 한다. 현재 핸들러는 계속 `mock` 외 모드를 거절한다.

## 정산 필드와 이용 기간 장부

`_replay_coaching_users/{sha256(uid)}`와 `_replay_coaching_months/{YYYYMM}`을 그대로 사용한다. 새 컬렉션이나 저장 서비스를 만들지 않았다. 기존 Firestore 클라이언트 접근 금지도 유지한다.

| 위치 | 필드 | 의미 |
| --- | --- | --- |
| 사용자 | `schemaVersion: 3`, `access`, `used`, `held` | 서버 이용 기간, 성공 횟수와 현재 예약 횟수(0/1) |
| 사용자 | `attempts`, `recent`, `previous` | 기간당 최대 70개 시도, 이전 두 기간만 보관. 종료 기록과 활성 예약의 수가 시도 횟수와 일치해야 함 |
| 활성 예약 | `id`, `digest`, `lease`, `period`, `units`, `stage`, 시각 | 작업·입력·실행 잠금·원래 비용 월·최대 비용·전송 상태 |
| 종료 기록 | `status`, `chargedUnits`, `costResolution`, ID/digest/lease | 성공/실패/취소/미확정 종료와 비용 확정 방식 |
| 전역 | `schemaVersion: 2`, `successfulCalls` | 사용자에게 정상 완료된 전체 횟수 |
| 전역 | `usedCalls`, `heldCalls` | 전송 후 종료된 생성 시도 수와 현재 예약 수. 실패도 시도 한도에 포함 |
| 전역 | `spentUnits`, `heldUnits` | 확정 비용과 최대액 예약 비용. 실패 비용도 합산 |

전역 호출 한도는 이제 `usedCalls + heldCalls`, 비용 한도는 `spentUnits + heldUnits`로 확인한다. 전송 전에 취소가 확정된 작업은 전역 생성 시도 수를 늘리지 않지만 개인 시도 기록에는 남긴다. 성공 횟수·시도 횟수·동시 예약·비용 제한을 서로 대체하지 않는다.

후속 [이용 기간 단계](replay-coaching-access.md)에서 서버 테스트 기간별 성공 최대 50회·시도 70개, 페이지 메모리 210개로 확장했다. 실제 결제 주기 조회·일별 제한·실제 마이크로달러·단가 버전은 후속 설계다.

**v1/v2 사용자 문서나 손상된 문서는 자동 초기화/변환하지 않고 `QUOTA_STATE_INVALID`로 거절한다.** 전역 비용 문서는 v2를 유지한다. 이 함수는 아직 운영에 배포하지 않았다. 기존 환경에 이전 사용자 데이터가 있다면 활성 예약과 비용을 확인하는 별도 이전 절차가 필요하며, 숫자를 0으로 초기화해 운영을 재개하면 안 된다. 로컬 테스트는 격리된 demo 데이터를 사용한다.

## 명시적 복구

`recoverCoachingQuota(db, uid, { requestId, lease, resolution }, now)`는 신뢰할 수 있는 서버 작업을 위한 함수다. HTTP 엔드포인트·브라우저 권한·자동 작업·운영 실행 CLI는 추가하지 않았다. 이번 검증에서 운영 DB에 실행하지 않았다.

운영자는 읽은 활성 작업의 ID와 현재 `lease`를 함께 지정해야 한다. 시작 후 최소 60초가 지난 작업만 복구하며, 이는 자동 만료 시간이 아니다.

| 선택 | 허용 상태 | 처리 |
| --- | --- | --- |
| `cancel_before_dispatch` | `reserved`만 | 비용 0, 사용자 예약 해제, `cancelled`로 종료 |
| `close_max_cost` | `dispatching`만 | 최대 예약액을 확정 비용에 남기고 사용자 예약 해제, `closed_unknown`으로 종료 |

전송한 작업을 전송 전 취소로 바꾸거나, 다른 작업/lease를 지정하면 거절한다. 이미 같은 lease로 종료한 작업의 복구 재요청은 기존 상태만 반환하며 비용이나 이용 횟수를 다시 바꾸지 않는다. 성공 작업을 복구 호출로 환불하지 않는다.

복구와 늦은 정상 정산이 동시에 들어오면 트랜잭션으로 한쪽만 최종 상태를 만든다. 먼저 정상 정산됐으면 그 결과를 유지한다. 먼저 최대 비용 종료됐다면 뒤늦은 완료는 오래된 lease로 거절된다. 다음 작업이 이미 시작됐어도 이전 실행이 그 작업을 정산할 수 없다.

월을 넘긴 활성 예약은 원래 월의 전역 문서에서 정산한다. 그 전에는 새 월이나 다음 이용 기간이라도 해당 계정의 새 작업을 막는다. 복구 후 새 이용 기간 집계를 만들더라도 이전 월의 확정 비용은 남는다. 달력 월만 바뀌면 사용자 집계는 유지한다. 실제 결제 주기 기준의 유료 이용권 복구/환불은 이번 범위에 없다.

## 검증 및 비용 변화

- 단위: 성공·실패의 비용 분리, 남은 예약액 해제, 실패 비용의 예산 반영, 비용 0인 실패도 전역 시도 한도 적용, 잘못된 정산/lease/중복 차단.
- 장애: 전송 시작 저장의 커밋 전/후 응답 유실, 정산 저장의 커밋 전/후 응답 유실, 전송 전 취소, 전송 후 최대 비용 종료, 반복 복구, 다음 작업 시작 후 이전 응답, 월 경계, v1/손상 장부 거절.
- Firestore Emulator: 실제 트랜잭션에서 실패 비용을 유지하고, 복구 2개와 정상 정산 1개의 경합에서도 최종 차감이 한 번인지 확인한다. 클라이언트의 장부 접근 금지와 기존 전역 동시 예약 테스트도 유지한다.
- 브라우저: 기존 로컬 모의 API의 로그인·한도·중복·응답 유실·파일 교체 흐름을 다시 검증한다.

신규 정상 모의 요청의 기본 DB 작업은 예약·전송 시작·정산 **트랜잭션 3회, 문서 읽기 6회·쓰기 5회**다. 기존보다 사용자 문서 읽기/쓰기와 전역 문서 읽기가 추가된다. 충돌 재시도·중복 확인·복구는 읽기 등을 추가로 쓸 수 있다. 이번 실행은 로컬 Emulator이며 운영 호출은 없다. 실제 활성화 전에는 기존 Firebase 무료 할당량·사용량을 다시 확인한다.

기간·한도·보관 수의 로컬 확장은 [이용 기간 문서](replay-coaching-access.md)에 정리했다. 결과 보관·재조회는 후속 내부 경로에서 로컬 구현했고 [실제 소액 생성 시험](replay-coaching-pilot.md)에서 정산도 확인했다. 의미 품질 기준은 미달이며 결제·운영 활성화는 별도로 남아 있다.
