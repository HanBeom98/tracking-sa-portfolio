# 홈 CSS 전달 방식 개선

2026-10-24. 홈의 공유 스타일을 별도 파일로 기다리던 경로를 줄였다. 빌드가 `src/shared/assets/style.css`의 현재 내용을 홈 `<head>`의 기존 스타일시트 위치에 삽입한다. CSS 규칙·적용 순서·화면 디자인은 동일하며, 홈 외 페이지는 기존 버전이 붙은 `/style.css` 링크를 유지한다. CSS를 별도로 복사해 관리하거나 런타임 로더를 추가하지 않는다.

## 비교 실험

공통 JS 지연 적용이 끝난 홈을 기준으로 외부 CSS와 인라인 CSS를 비교했다. Chromium 145.0.7632.6, 390×844 CSS px, CPU 4배 감속, 지연 150ms·다운로드 200,000 bytes/s·업로드 100,000 bytes/s. 로컬 서버는 HTML과 자산을 gzip으로 전송했다. 외부 서비스와 서비스 워커를 차단해 실제 API/DB를 호출하지 않았다.

새 브라우저 컨텍스트에서 첫 방문을 측정한 다음 같은 컨텍스트에서 재방문했다. HTTP 캐시는 활성화하고 외부 CSS를 장기 캐시했다. 두 방식을 ABBAAB 순서로 실행해 각 방식·방문 상태마다 3개 표본을 얻었다. 실험의 인라인 HTML과 실제 빌드 결과가 동일함을 확인했다.

| 지표 | 외부 CSS 중앙값 (범위) | 인라인 CSS 중앙값 (범위) |
| --- | --- | --- |
| 첫 방문 FCP | 780ms (776–796) | 232ms (228–240) |
| 첫 방문 LCP | 780ms (776–796) | 600ms (596–612) |
| 재방문 FCP | 240ms (236–248) | 220ms (216–224) |
| 재방문 LCP | 240ms (236–248) | 252ms (252–256) |

첫 방문 LCP 중앙값은 180ms, 약 23% 줄었다. FCP는 최초의 일부 콘텐츠 표시이므로 232ms에 홈 본문 전체가 표시됐다는 뜻은 아니다. 재방문 LCP는 12ms 늘었으며 재방문 속도 개선을 주장하지 않는다. LCP 요소는 양쪽 모두 홈의 장식용 `::after`였다.

측정용 HTML은 gzip 8,579→11,806 bytes로 약 3.2KB 증가한다. 첫 화면에서 공유 CSS 요청 1개를 기다리지 않는 대신, 공유 스타일을 HTML과 함께 재전송한다. 홈 다음에 다른 페이지로 이동할 때 공유 CSS가 아직 캐시되지 않았다면 그 페이지가 별도로 다운로드한다. 같은 로컬 조건의 홈→전적 페이지 점검 각 1회에서는 FCP 564→568ms였지만, 표본이 하나여서 영향이 없다고 일반화하지 않는다.

이 결과는 외부 광고·Firebase 비용을 포함하지 않은 통제 실험이다. 사용자가 제공한 실제 PageSpeed 62점·FCP 4.7초·LCP 7.2초와 직접 비교하지 않으며, 운영 점수 상승은 별도 측정이 필요하다. 로컬 실험을 근거로 홈에만 적용했다.

## 회귀 확인

- 빌드된 홈에 원본 CSS 전체가 정확히 한 번 들어가고 다른 페이지는 외부 링크를 유지한다.
- CSS의 삽입 위치와 나머지 head 내용이 보존되고, CSS 원본 수정은 다음 빌드에 반영된다.
- 390/1280px와 밝은/어두운 테마 4개 조합에서 외부 CSS 기준 화면과 요소 위치·크기·색상·글꼴·여백을 비교한다.
- 홈이 외부 공유 CSS를 요청하지 않아도 검색 입력·모바일 메뉴·테마 전환이 동작한다.
- 기존 검색·공지·인증·광고 검증은 기존 테스트 흐름을 유지한다.

새 유료 상품, 서버 요청, 측정 SDK, 스케줄 작업은 추가하지 않았다. 광고 설정·인증 SDK 로딩 시점은 이번 변경 범위에 포함하지 않는다.

CSS 인라인은 추가 요청을 줄이지만 HTML 크기와 캐시 재사용에 영향을 준다. [Google의 CSS 전달 설명](https://web.dev/articles/extract-critical-css)을 참고하고 실제 스타일 크기와 첫 방문·재방문을 함께 측정했다.
